# Off-repo GeoJSON data (`data.bikenetkit.org`)

The per-city tool layers (`www/data/`) are served as **plain static GeoJSON from the project's
own server**, not committed to git. They are ~1 GB today and scale to many GB as the city catalog
grows (SuperBlockify alone applies to every city), which would otherwise bloat the repo, the
`.git` history on every data refresh, and every clone past workable limits.

Like the basemap, there is no API key and no third-party service in the runtime path — it stays
within the ~8-year no-maintenance goal.

## How the pieces fit

- **The build never reads or ships the data.** `www/data/` is gitignored, and deliberately sits _outside_ `static/` so Vite's public-dir copy never duplicates it into `build/`. The app enumerates datasets
  from the committed [src/lib/data/data-files.json](src/lib/data/data-files.json) manifest
  (generated by `update-data`; parsed by [src/lib/data/datasets.ts](src/lib/data/datasets.ts)), and
  fetches the GeoJSON in the browser at runtime.
- **`PUBLIC_DATA_URL`** prefixes every data fetch (via `dataUrl()` in
  [src/lib/data/data-base.ts](src/lib/data/data-base.ts), used by `tool-paths.ts` and
  `boundaries.ts`). Empty → same-origin `/data/…` (local dev). Absolute → the subdomain.
- **One endpoint, all environments.** A cross-origin `GET` for GeoJSON is a CORS _simple request_
  (no preflight), so pointing every environment at `data.bikenetkit.org` costs nothing measurable.
- **Per-dataset screenshots ride the same host** under `/screenshots` (~570 MB at ~400 cities, also
  gitignored). `screenshotFor()` in `tool-paths.ts` routes them through the same `dataUrl()`, which
  leaves the `/screenshots` path intact → `${PUBLIC_DATA_URL}/screenshots/…`. `pnpm deploy:data`
  uploads `www/screenshots/` to `…/data/screenshots/` alongside the GeoJSON. Regenerate with
  `pnpm generate:screenshots` (needs a production build — see that script's config).
- **So do the per-city Open Graph cards**, under `/screenshots/og/` (~85 MB, one card per city and
  one per tool × covered city). `pnpm generate:og-cards` captures them into `www/screenshots/og/`
  and rewrites the committed `src/lib/data/og-cards.json`, which is what lets a page use its card:
  an unlisted card falls back to the tool's own. The cards ride the screenshot sync, so **run
  `pnpm deploy:data` before the site deploy that commits a newer manifest**, or the new pages
  preview with an image the data host does not have yet. `pnpm check:og-cards` compares the
  manifest with the files on disk. The cards are JPEG, not WebP, so the vhost needs its own
  `\.jpg$` location (see § nginx); without it every card 404s while the files sit on the server.

| Environment                          | `PUBLIC_DATA_URL`                                    |
| ------------------------------------ | ---------------------------------------------------- |
| Production (`bikenetkit.org`)        | `https://data.bikenetkit.org`                        |
| Preview host (`pnpm deploy:preview`) | `https://data.bikenetkit.org` (forced by the deploy) |
| Local dev                            | _(empty)_ → local `www/data/` via the Vite plugin    |

The placeholder page's hero map (`AmbientMapPane.svelte`) fetches its GeoJSON client-side in the
browser via `geojsonPathFor()`, so it needs a reachable `PUBLIC_DATA_URL` too — same as the full
site. `www/.env` leaves `PUBLIC_DATA_URL` empty for local dev, which would resolve to same-origin
`/data/…` and 404 once `data/` is excluded from the deploy rsync. `pnpm deploy:site`,
`pnpm deploy:preview` and `pnpm deploy:placeholder` (`scripts/deploy.mjs`) all override this automatically, forcing
`PUBLIC_DATA_URL` to `DEPLOY_PUBLIC_DATA_URL` (`www/.env`, defaults to `https://data.bikenetkit.org`)
for the build they run — no manual `www/.env` edit needed before deploying.

## The build is independent of the data

`pnpm build` never reads a byte of GeoJSON. It needs neither `www/data/` on disk nor a reachable
`data.bikenetkit.org`, and a clean clone builds the identical set of pages.

Three things get it there:

- **The map pages fetch in the browser, not at prerender.** Their `load()` is synchronous and
  fetch-free; the layers are fetched on hydration by
  [src/lib/data/active-dataset.svelte.js](src/lib/data/active-dataset.svelte.js), owned by the
  `(map)` layout. The prerendered shell keeps its per-city title, description and panels, so
  crawlers and shared links lose nothing. `svelte.config.js`'s `handleHttpError` therefore has no
  `/data/…` branches — the prerenderer never requests a dataset.
- **The route set comes from the manifest.** `entries()` reads `data-files.json`, not a
  `readdir` of the data tree, so the prerendered pages no longer depend on whether the building
  machine holds the data. (Before, a clean clone silently emitted only the ~403 fallback pages per
  tool.)
- **The data lives outside `static/`.** `www/data/` and `www/screenshots/` are served in dev and
  preview by the `offRepoData` middleware in [vite.config.js](vite.config.js), so local work stays
  offline-capable without the build copying ~2.4 GB into `build/` on every run.

**Two invariants moved into the build-time preflight**, the `init` hook in
[src/hooks.server.ts](src/hooks.server.ts), which is where they now fail — in seconds, before the
prerender, rather than mid-crawl on a 404:

- a tool the manifest lists no datasets for;
- a linkbikenet city missing its **mandatory** existing-network baseline. (fixbikenet's is
  optional — 15 of its 398 cities legitimately ship without one.)

> The root [src/routes/+layout.ts](src/routes/+layout.ts) carries `export const prerender = true`,
> which every other route inherits. Removing it un-prerenders the entire map section, and the
> build still goes green. It is a universal file on purpose: a `+layout.server.ts` on the root
> layout, even one without a `load`, makes the client fetch `__data.json` before every route, and
> the client-only `/embed` then 404s on a static host.

## Regenerating the data + manifest

A plain pull refreshes every tool (all of them, SuperBlockify included, now ship in the server
export):

```sh
pnpm pull-data   # rsyncs the latest server export (all tools) and transforms it
```

On macOS, install GNU rsync first (`brew install rsync`). The system `rsync` is openrsync, which
stalls partway through a pull this size. `pull-data` and `pull-screenshots` warn when they detect it, and their
`--timeout=120` turns a stall into an error, so a re-run resumes instead of hanging.

The run rewrites `data-files.json` from the **complete** `www/data/` tree, so a filtered
`--tool` run never drops a tool. To refresh only the manifest + boundaries without touching a data
root:

```sh
node scripts/update-data.mjs --boundaries-only
```

## Uploading

```sh
pnpm deploy:data -- --dry-run
pnpm deploy:data
pnpm deploy:data -- --force   # mirror www/screenshots/ exactly even when sparse (see below)
```

Rsyncs `www/data/` to `DEPLOY_DATA_WEB_PATH` (`~/bikenetkit/data/`). Like the basemap dir, the
target is deliberately **not** under `~/bikenetkit/website/`: `pnpm deploy:site` syncs that with
`--delete` and would erase the data. `deploy:data` uses `--delete` within its own dedicated dir, so
the served data stays an exact mirror of `www/data/` (stale cities/layers are pruned). That
includes `www/data/context/`, the rail station and school points written by `pnpm import:context`
(which `pnpm pull-data` runs). Because a mirror without them would delete them from the data host,
`deploy:data` aborts when `www/data/context/` is missing or empty.

Commit `data-files.json` (and the other `src/lib/data/*.json`), then run `pnpm deploy:site`, so the
build matches the uploaded data.

### Screenshot coverage guard

Unlike `www/data/`, `www/screenshots/` is generated locally over hours
(`pnpm generate:screenshots`), not pulled from the server export; a fresh checkout seeds it from the
data host with `pnpm pull-screenshots` (below). Every run of `deploy:data`
prints a coverage report ([scripts/screenshot-coverage.mjs](scripts/screenshot-coverage.mjs))
comparing `www/screenshots/` against the datasets `www/data/` actually holds — the same
city × metric × type × variant matrix `generate:screenshots` itself iterates:

```
[data] screenshots: 4700 / 6281 (75%)
         growbikenet     4612 /  4612
         fixbikenet         5 /   398
         linkbikenet        9 /  1197
         superblockify     74 /    74
```

(The Sep 2026 export took FixBikeNet from 5 cities to 398 and LinkBikeNet from 3 to 399, so the
two of them account for the whole shortfall — regenerating their screenshots is the outstanding
work. SortBikeNet does not appear: the matrix follows the active interactive tools, and it is
still `coming-soon`.)

- **100% coverage** — synced as normal, with `--delete` (exact mirror).
- **Below 100%, at or above 90%** — a one-line note; synced with `--delete` (a few stragglers
  during otherwise-finished generation are expected).
- **Below 90% ("sparse")** — a WARNING, and the sync drops `--delete`: it becomes purely additive,
  so a partial local set can never prune screenshots already on the server. Pass `--force` to
  mirror exactly anyway (the server ends up matching this partial set).

- **Zero screenshots present** — the screenshot sync is skipped entirely (nothing to add, and an
  empty tree must not touch the server's existing set).

**A fresh checkout starts at 0%.** Run `pnpm pull-screenshots` once before generating anything: it
fetches the server's set (~610 MB, OG cards included) into `www/screenshots/`. It only adds —
no `--delete`, and `--update` keeps any local image newer than the server's copy — so it is also
safe to re-run on a checkout that has unuploaded screenshots. Without it, `generate:og-cards`
rewrites `og-cards.json` from the few cards that exist locally.

The GeoJSON sync above is never gated by this check.

Non-`.geojson` files under `www/data/` (the `cities/*.csv` build-time inputs to `update-data`)
ride along in the rsync but are never fetched at runtime — the nginx `location / { return 404; }`
makes them inert on the host.

## nginx

A dedicated vhost for `data.bikenetkit.org` serving `~/bikenetkit/data/`. Unlike the tiles vhost,
gzip is **on** — GeoJSON compresses ~3–5×. The per-dataset screenshots live under `/screenshots/`
in the same dir and are served by a second `location` (webp is already compressed, so it is left
out of `gzip_types`; `<img>` loads need no CORS header).

**Serve the pre-compressed siblings, don't compress per request.** `gzip on;` on its own uses
nginx's default `gzip_comp_level 1`, the weakest setting, and pays that CPU on every single
request. `pnpm compress:data` writes `.gz` and `.br` next to each `.geojson` on the server, and
`gzip_static` / `brotli_static` hand them straight out. Measured on the largest layer
(`berlin_de-residential-edges.geojson`, 18.85 MB):

| served as                           |    size |
| ----------------------------------- | ------: |
| `gzip_comp_level 1` (nginx default) | 3.21 MB |
| `gzip_comp_level 6`                 | 2.62 MB |
| `gzip_static`, gzip -9              | 2.53 MB |
| `brotli_static`, brotli -q 10       | 1.85 MB |

`gzip_static` is in nginx core. `brotli_static` comes from a module package, and on Ubuntu 26.04
the brotli support is **split in two** — there is no `libnginx-mod-http-brotli`:

```sh
sudo apt install brotli \
  libnginx-mod-http-brotli-filter \
  libnginx-mod-http-brotli-static
```

`-static` is the one that provides `brotli_static`; `-filter` provides on-the-fly `brotli` and is
not strictly needed here, but installing both keeps the directive set complete. Installing them
drops `50-mod-http-brotli-*.conf` into `/etc/nginx/modules-enabled/`, so no `load_module` line is
needed. **Without the module, `brotli_static on;` makes nginx fail to start** — install first,
`sudo nginx -t`, then reload. If it is unavailable, drop that line and keep `gzip_static` alone;
`compress-data.mjs` likewise skips `.br` when the `brotli` CLI is missing.

Keep `gzip on;` below as the fallback for anything without a sibling (a dataset uploaded but not
yet compressed); `gzip_static always;` is deliberately not used, since that would serve a stale
`.gz` in preference to a newer source.

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name data.bikenetkit.org;

    root /home/<SSH_USER>/bikenetkit/data;

    # Security headers (DEPLOY_NGINX.md § Security headers), repeated in every location below:
    # each sets its own add_header, which discards the server-level ones.
    include snippets/bikenetkit-security.conf;

    # Truncate the client IP before it is logged, like the site vhost. The format is defined in
    # conf.d/anonymized-log.conf — see DEPLOY_NGINX.md; the privacy notice at /legal#privacy says
    # no full address is stored anywhere, and that has to hold on this host too.
    access_log /var/log/nginx/access.log anonymized;

    # Prefer the pre-compressed siblings written by `pnpm compress:data`. Drop the brotli_static
    # line if libnginx-mod-http-brotli-static is not installed — nginx refuses to start without it.
    gzip_static on;
    brotli_static on;

    # Fallback for anything with no sibling yet. Level 6 rather than the default 1: the default
    # leaves ~20% on the table, and this path should be rare once compress:data has run.
    gzip on;
    gzip_comp_level 6;
    gzip_types application/geo+json application/json;
    gzip_min_length 1024;

    location ~ \.geojson$ {
        include snippets/bikenetkit-security.conf;
        default_type application/geo+json;

        add_header Access-Control-Allow-Origin  "*" always;
        add_header Access-Control-Allow-Methods "GET, HEAD, OPTIONS" always;

        # Data is regenerated in place, so do not cache forever. A modest TTL + revalidation
        # keeps previews fresh; bump it once the dataset is stable.
        add_header Cache-Control "public, max-age=3600" always;

        if ($request_method = OPTIONS) { return 204; }

        try_files $uri =404;
    }

    # Per-dataset preview screenshots (pushed to /screenshots/ by `pnpm deploy:data`). Loaded via
    # <img>, so no CORS header is needed; already-compressed webp is not gzipped.
    location ~ \.webp$ {
        include snippets/bikenetkit-security.conf;
        default_type image/webp;
        add_header Cache-Control "public, max-age=3600" always;
        try_files $uri =404;
    }

    # Per-city Open Graph cards (pushed to /screenshots/og/ by `pnpm deploy:data`). Fetched by
    # social crawlers, so no CORS header; already-compressed jpeg is not gzipped.
    location ~ \.jpg$ {
        include snippets/bikenetkit-security.conf;
        default_type image/jpeg;
        add_header Cache-Control "public, max-age=3600" always;
        try_files $uri =404;
    }

    location / { return 404; }
}
```

```sh
sudo ln -sf /etc/nginx/sites-available/bikenetkit-data /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

TLS, once the DNS A record for `data.bikenetkit.org` points at the server:

```sh
sudo certbot --nginx -d data.bikenetkit.org
```

## Verifying

**Locally**, without uploading — serve `www/data/` cross-origin and point the app at it:

```sh
npx --yes http-server data -p 8082 --cors
# www/.env: PUBLIC_DATA_URL=http://localhost:8082
pnpm build && pnpm preview
```

Open an interactive tool page and confirm the map layers and city boundaries load from
`localhost:8082` (cross-origin 200s in devtools). With `PUBLIC_DATA_URL` **empty**, the same pages
must load from local `www/data/` via the `offRepoData` middleware, in both `pnpm dev` and
`pnpm preview`.

**Clean build** — rename `www/data/` away and build with `PUBLIC_DATA_URL` unset. It must
**succeed**: nothing is fetched at prerender any more, so neither the files nor a reachable host is
required. Confirm the output carries no data at all:

```sh
du -sh build                                   # ~200 MB, and no build/data or build/screenshots
grep -c coordinates build/growbikenet/<city>/<metric>/<type>/<variant>.html   # expect 0
find build/growbikenet -name '*.html' | wc -l  # unchanged with the data absent
```

That last count is the point of enumerating from the manifest: the prerendered route set no longer
depends on whether the building machine happens to hold the data.

**The server** — before DNS exists, address the vhost by Host header:

```sh
curl -sI -H 'Host: data.bikenetkit.org' \
  http://<server-ip>/cities/amsterdam-boundary.geojson
# expect: 200, Access-Control-Allow-Origin: *, Content-Encoding: gzip
```

**The pre-compressed siblings** — after `pnpm compress:data`, confirm the static variants are the
ones being served, and that they are smaller than the on-the-fly fallback:

```sh
# brotli_static: expect Content-Encoding: br and a content-length near the .br on disk
curl -sI -H 'Host: data.bikenetkit.org' -H 'Accept-Encoding: br' \
  http://<server-ip>/superblockify/berlin_de-residential-edges.geojson

# gzip_static: expect Content-Encoding: gzip at ~2.53 MB, not the ~3.21 MB of level 1
curl -sI -H 'Host: data.bikenetkit.org' -H 'Accept-Encoding: gzip' \
  http://<server-ip>/superblockify/berlin_de-residential-edges.geojson
```

A `Content-Encoding: gzip` response at ~3.21 MB means `gzip_static` is not matching and nginx is
compressing per request — check the `.gz` exists next to the source and that the module is loaded.
